# Reflection

## Security

The application uses a Hugging Face access token, which is stored in `.env` instead of being hard-coded in the source code. This prevents sensitive credentials from being committed to the repository.

The API accepts uploaded CSV files, which introduces potential security risks such as invalid or malicious files. Basic validation is performed before processing the upload but additional validation such as file size limits and MIME type verification would improve security in a production environment.

The AI component is also susceptible to prompt injection if user input is embedded directly into prompts. To reduce this risk, the prompt is structured with fixed system instructions and dataset statistics. However, a production-ready application would require more robust prompt validation and sanitization.

## GDPR

The application stores uploaded datasets only in memory and does not persist data after the application terminates. This mitigates long-term storage of potentially sensitive information.

If the application were deployed in production, GDPR compliance would require additional measures such as informing users how their data is processed, defining retention policies, handling deletion requests as well as ensuring that personal data is processed securely and lawfully.

## AI

The project uses the **HuggingFaceTB/SmolLM2-135M-Instruct** model through the Hugging Face `transformers` library as well as the `torch` library which handles the hardware side of running the LLM locally.

Because SmolLM is a relatively small language model, the quality of its responses varies depending on the prompt and the available context. During development, prompt engineering became an important part of achieving useful answers. Dataset statistics generated with `pandas.DataFrame.describe()` were included in the prompt to provide the model with structured context while keeping the prompt reasonably small.

Like all language models, SmolLM can generate inaccurate or fabricated information (hallucinations). For this reason, responses generated by the model should not automatically be considered correct without verification.

### Testing

Testing the AI component also presented challenges because language model output is non-deterministic. To improve reliability, the Runnable components were tested independently, while the LLM itself was mocked during automated testing.

Additionally, a clear takeaway from the project is that automated e2e testing would increase the effectiveness of prompt engenering and would be most benefical when implemented early in the development cycle. However, this approach would require ongoing maintence and development of the test to ensure continued functionality.

## Design

The project is built around a custom Runnable architecture consisting of three processing steps:

* PromptBuilder
* LLMRunner
* ResponseParser

Each component has a single responsibility, making the application easier to understand, maintain and test. The pipeline is composed using the `|` operator, allowing each Runnable to remain independent while still forming a complete processing chain.

One of the biggest challenges during development was integrating the Runnable pipeline with the Hugging Face `transformers` pipeline. The interdependance between each chain component complicated development as it was more difficult to isolate and refactor the code. Refactoring resulted in frequent "type juggling" creating opportunity for validation errors.

Building prompts that produced reliable responses from the language model required several iterations. Understanding how the prompt structure, dataset context and response parsing interacted with the model took time during development, second only to the pipeline integration.

Overall, the project demonstrates separation of concerns through dedicated modules for API endpoints, data management, configuration, schemas and Runnable processing. This modular structure makes future extensions and testing more straightforward.

### Challenges
During development, Pydantic validation helped identify integration issues between Runnable steps. Trial and error was one stratigy used for iterative development which at one point meant that a component returned a CSV string while the next expected a list, resulting in a validation error. Strong typing made the source of the problem easy to identify and fix before it propagated through the pipeline.

Another challenge was prompt engineering. Early prompts caused the model to ignore the user's question and generate unrelated examples or additional questions. Several prompt structures were tested before a format was found that produced consistently useful responses. This demonstrated that small instruction-tuned language models are highly sensitive to prompt design.

Integrating the Hugging Face transformers pipeline required understanding generation parameters such as max_new_tokens and prompt formatting. Incorrect prompt construction initially resulted in empty model output, which was resolved by restructuring the prompt and adjusting the generation settings.

### Solution
Rather than implementing the complete AI workflow at once, each Runnable component was developed and tested independently before being integrated into the final pipeline. This incremental approach made debugging significantly easier and helped isolate issues between individual processing steps. However, due to the interconnectivity between `PromptBuilder` `LLMRunner` and `ResponseParser` later iterations resulted in concurrent enhancements and debugging to ensure end-to-end funtionality of the pipeline chain.
